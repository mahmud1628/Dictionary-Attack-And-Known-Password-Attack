# Project: Dictionary Attack and Known Password Attack on an HTTP Login System

## Goal

Build two programs from scratch:

1. A **victim web server** with an HTTP login endpoint (the target).
2. A **custom attack tool** that performs a **dictionary attack** and a **known password attack** against that server.

This is an academic cybersecurity project. Everything runs locally against our own server.

## Hard Constraints (must follow)

- **No existing attack tools** (no Hydra, Hashcat, Burp, etc.).
- **No high-level HTTP client libraries in the attack tool** (no `requests`, `urllib`, `http.client`, `aiohttp`). The attack tool must **craft the raw HTTP request as a byte string by hand and send it over a raw TCP socket** (`socket` module only).
- Language: **Python 3** for both programs.
- Protocol: **HTTP** (plain, no HTTPS/TLS).
- The victim server **may** use a normal web framework (Flask) and the standard library (`sqlite3`, `hashlib`) — the "no libraries" rule applies only to the **attack tool**.

## Repository Layout

The project is split into two independent folders: the target (`server/`) and the
attacker (`attacker/`). Nothing in `attacker/` imports from `server/`; the only link
between them is HTTP over a raw socket.

```
project/
├── server/
│   ├── victim_server.py     # target web server (Flask)
│   ├── seed_db.py           # creates + seeds users.db (run once, before serving)
│   ├── auth.py              # shared hash_password() helper (used by both files)
│   └── users.db             # SQLite database (generated by seed_db.py)
│
├── attacker/

│   ├── wordlist.txt         # candidate passwords (dictionary attack)
│   └── credentials.txt      # user:pass pairs (known password attack)
│
├── PROJECT.md
└── README.md                # how to run
```

> **Note on layout:** this differs from a flat single-folder layout. All required
> functionality is preserved; the README documents where each piece lives.

## Data Storage — SQLite (`server/users.db`)

Accounts and the attempt log live in a single **SQLite** database file, created and
seeded by `seed_db.py`. Two tables:

### `users` table (account credentials — hashed)

| column          | type             | notes                              |
| --------------- | ---------------- | ---------------------------------- |
| `username`      | TEXT PRIMARY KEY | the login id                       |
| `salt`          | TEXT             | random per-user salt               |
| `password_hash` | TEXT             | salted **PBKDF2** hash of password |

- Passwords are **never stored in plaintext**. Hashing uses `hashlib.pbkdf2_hmac`
  with a random per-user salt.
- Hashing protects the *stored* credentials (e.g. if `users.db` is stolen); it does
  **not** defend against online guessing — that is the point the attacks demonstrate.

### `log` table (attempt log — plaintext attempts)

| column      | type                             | notes                          |
| ----------- | -------------------------------- | ------------------------------ |
| `id`        | INTEGER PRIMARY KEY AUTOINCREMENT | row id                         |
| `timestamp` | TEXT                             | ISO datetime of the attempt    |
| `client_ip` | TEXT                             | client that sent the request   |
| `username`  | TEXT                             | submitted username             |
| `password`  | TEXT                             | **attempted** plaintext password |
| `result`    | TEXT                             | `SUCCESS` or `FAIL`            |

- The **attempted** password is logged in plaintext on purpose: the log's job is to
  capture exactly what the attacker tried, so the attack can be inspected afterward.
- Note the intentional asymmetry: stored account passwords are **hashed**, but logged
  attempt passwords are **plaintext**.

### `server/auth.py` — shared hashing helper

Both `victim_server.py` and `seed_db.py` import the **same** `hash_password()` from
`auth.py`, so the seeding side and the verification side can never drift apart.

## Part 1 — Victim Web Server (`server/victim_server.py`)

A minimal Flask app. Kept simple; it is the target environment, not the focus.

### Requirements

- Serves on `0.0.0.0:8080` (configurable via a constant at top of file).
- Reads accounts from `users.db` (seeded beforehand by `seed_db.py`). Seed accounts:
  ```
  admin        : hello123
  john@mail.com: sunshine99
  mary@mail.com: football22
  ```
  (Stored hashed, not plaintext — see Data Storage above.)

### Endpoints

- **`GET /login`** — the human-facing form.
  - Takes no input, does no authentication, writes no log.
  - Returns HTTP **200** with `Content-Type: text/html`: a tiny HTML page with a
    `<form method="POST" action="/login">` (username field, password field, submit),
    so a human can test in a browser. Submitting it sends a `POST /login`.

- **`POST /login`** — the actual authentication endpoint (the real target).
  - Accepts `application/x-www-form-urlencoded` body with `username` and `password`.
  - Looks up the username in the `users` table, hashes the submitted password with the
    stored salt (via `auth.hash_password`), and compares to `password_hash`.
  - On correct credentials → HTTP **200**, body contains the word `Welcome`.
  - On wrong credentials **or unknown username** → HTTP **401**, body contains the word
    `Invalid`. (Unknown-user and wrong-password return the *same* response, to avoid
    leaking which usernames exist.)
  - Uses parameterized SQL queries (`?` placeholders) — not string concatenation.

### Logging

- Append **every** `POST /login` attempt to the `log` table (see schema above), with
  `result` = `SUCCESS` or `FAIL`, regardless of outcome.

### Defense mechanism

- **To be decided.** No defense/lockout is implemented in the base version so the
  attacks succeed cleanly. A mechanism (e.g. rate limiting, lockout, or something else)
  will be chosen and added later as the "defense demonstration".

## Part 2 — Attack Tool (`attacker/attack_tool.py`)

A single Python program with two modes. **Raw sockets only.**

### Command-line interface

```
python attack_tool.py --target <ip> --port <port> --mode dictionary --username <user> --wordlist wordlist.txt
python attack_tool.py --target <ip> --port <port> --mode known --credentials credentials.txt
```

Use `argparse`. Defaults: `--port 8080`, path defaults for the two files.

### Internal components (keep as separate functions)

1. **`url_encode(value)`**
   - Percent-encode reserved characters (`@`, `&`, `=`, space, `+`, `%`, etc.) so the body never breaks.
   - Do this yourself (small lookup / `%XX` formatting). Do **not** import a URL library.

2. **`craft_packet(host, username, password)` → bytes**
   - Builds the raw HTTP POST request string.
   - Body: `username=<enc>&password=<enc>`.
   - **Must compute `Content-Length` as the exact byte length of the body.**
   - Template:
     ```
     POST /login HTTP/1.1\r\n
     Host: <host>\r\n
     User-Agent: Mozilla/5.0\r\n
     Content-Type: application/x-www-form-urlencoded\r\n
     Content-Length: <len(body)>\r\n
     Connection: close\r\n
     \r\n
     <body>
     ```
   - Return the whole thing encoded to bytes.

3. **`send_packet(target, port, raw_bytes)` → response string**
   - Open a TCP socket, connect, send all bytes, receive the full response, close.
   - Use `Connection: close` semantics (read until the server closes / recv returns empty).

4. **`parse_response(response)` → bool (success?)**
   - Determine success. Check the **status line** for `200` AND/OR the body for the `Welcome` keyword. Treat `401` / `Invalid` as failure.
   - Make success detection robust (a helper that returns True only on a clear success signal).

5. **`log_result(username, password, success)`**
   - Print each attempt to stdout, e.g.:
     ```
     [-] admin : 123456   -> FAIL
     [+] admin : hello123 -> SUCCESS
     ```

### Mode A — Dictionary Attack

- Input: one fixed `--username`, and `wordlist.txt` (one password per line).
- For each password: craft → send → parse → log.
- **Stop on the first success**, print the found password.
- At the end print a summary: total attempts, time elapsed, result.

### Mode B — Known Password Attack

- Input: `credentials.txt`, one `username:password` pair per line.
- For each pair: craft → send → parse → log.
- **Continue after a success** (goal is to find *all* accounts that work).
- At the end print a summary: number of valid accounts found out of total, list them, time elapsed.

### Robustness

- Handle connection errors per attempt (timeout, refused) without crashing — log and continue.
- Set a socket timeout (e.g. 5s).

## Part 3 — Input Files

### `attacker/wordlist.txt`
- A few hundred candidate passwords, one per line.
- Mix of: common passwords (`123456`, `password`, `qwerty`, `letmein`), keyboard walks (`asdfgh`, `1qaz2wsx`), name/season+number (`admin2024`, `Summer2024`), leetspeak (`p@ssw0rd`, `l3tm3in`).
- **Must include `hello123`** so the dictionary attack against `admin` succeeds.

### `attacker/credentials.txt`
- ~100 `username:password` pairs.
- Most should fail. **Include at least two that match seeded accounts**, e.g.:
  ```
  john@mail.com:sunshine99
  mary@mail.com:football22
  ```
  so the known password attack finds them.

(You can generate both files programmatically or as static files — either is fine.)

## How to Run (target for the README)

```
# one-time — create and seed the database
cd server
python seed_db.py

# terminal 1 — start the victim
python victim_server.py

# terminal 2 — dictionary attack (finds admin's password)
cd attacker
python attack_tool.py --target 127.0.0.1 --port 8080 --mode dictionary --username admin --wordlist wordlist.txt

# terminal 2 — known password attack (finds reused accounts)
python attack_tool.py --target 127.0.0.1 --port 8080 --mode known --credentials credentials.txt
```

## Expected Behaviour (acceptance criteria)

1. Server runs and a human can log in via browser at `http://127.0.0.1:8080/login`.
2. Dictionary attack against `admin` finds `hello123` and stops.
3. Known password attack finds the reused accounts (`john`, `mary`) and continues to the end.
4. The `log` table in `users.db` records every attempt with SUCCESS/FAIL.
5. The attack tool uses **only raw sockets** — verify there is no `requests`/`urllib`/`http.client` import in `attack_tool.py`.
6. `Content-Length` in crafted packets always matches the body length.
7. Account passwords are stored **hashed** (salted PBKDF2) in the `users` table, never in plaintext.

## Notes

- Keep the attack tool readable and well-commented, especially `craft_packet` — the manual packet construction is the core of the project.
- Sequential attempts are fine; no threading required.
- A defense mechanism will be selected and added later; the base version has none.
